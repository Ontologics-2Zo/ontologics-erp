# ontologics 객체 중심 작업공간

2026-11-04 재설계. 기존 React 19·TypeScript·Vite, Radix Dialog, TanStack Table을 유지한다. 이전 9개 업무 화면과 도메인 계산을 재사용하면서 객체 탐색·구매·전체 지도·운영 감사를 추가한다. 프레임워크 이전이나 실제 외부 실행은 하지 않는다.

화면 분리는 업무 책임과 입력 복잡도에 따른다. 같은 객체의 속성·근거·관계 확인은 공통 Inspector로 모으고, 복잡한 등록·검토·수량 입력은 해당 업무 화면에 유지한다. 전체 지도는 기본 탐색을 대신하지 않는다.

## 읽기 순서와 공통 맥락

공통 헤더에서 개발 계정·회사 범위·선택 대상·데이터 기준을 식별하고, 본문에서 수량/상태와 가능한 다음 행동을 확인한다. 탐색 경로는 **최근 선택한 객체의 경로**이며 실제 BOM 상하위 분류나 생산 공정 순서를 뜻하지 않는다.

선택은 이름·행 순서가 아니라 객체 유형, 회사 범위, 불변 ID, 버전으로 유지한다. 같은 품목이 여러 위치에 쓰이면 품목 식별은 재사용하되 BOMItem과 RefDes를 별도로 보존한다. 설계 BOM, 실제 장착 사건, 생산 라우팅은 다른 관계 모드다.

우측 보조 영역은 업무 AI와 Inspector를 전환하여 사용한다. AI와 Inspector 두 열을 동시에 고정해 중앙 업무를 좁히지 않는다. 좁은 화면에서는 보조 영역을 접거나 전환하고 표는 가로 스크롤을 사용한다. AI 없이도 조회·입력·검토가 가능하다.

선택·정렬·사진 확대·테마·패널 변경은 읽기/표현 동작이다. LLM 호출이나 원장 쓰기를 하지 않는다. AI 질문은 명시적 전송 시 AgentPort로 전달하며 요청 당시 객체·회사·시점·원장/초안 버전을 고정한다. 대상/계정 변경 후 늦은 응답은 새 맥락에 넣지 않는다.

## 대표 업무 흐름

1. **제품/BOM 등록**: `UI02`에서 포함된 원본/지원 파일 선택 → 원문과 추출 행·경고 확인 → 구성·품목 매핑 검토 → 초안 저장 → `UI05` 검토 요청 → 다른 개발 계정의 정확 버전 승인 → 반영 요청 → `UI02`/`EXPLORE`에서 같은 구성 재조회. 업로드·승인·반영은 각각 다른 상태다.
2. **부족 자재 검토**: `UI01`의 자재 조치 대상 → `MATERIAL`의 동일 수요·구성 → 필요/가용/자기 예약/부족 근거 → 원품·적용 승인 대체·미승인 후보 비교 → `UI07` 예약 또는 `PURCHASE` 구매 요청 초안. C7 한정 승인을 C8에 확대하지 않는다.
3. **로트에서 납품 조사**: `EXPLORE` 로트 선택 → 근거 있는 장착 사건 → 개별 보드 → 확인된 출하 연결 → 회차. 이력이 누락되면 누락 지점에서 미확인을 유지한다. `UI04`에서 시점/기간과 확인 범위를 검토하고 필요한 경우 보완안→승인→같은 조건 비교를 수행한다.
4. **약속 이행**: `UI08` 계약 회차 → 부분 생산실적 초안 → 검토·반영 → 완성품 입고 초안 → 검토·반영 → 명시 회차 배정 → 분할 출하 → 부분 도착. 각 사건과 원천을 연결한다. 남은 약속은 추가 생산량이 아니다.
5. **품질 대응**: `UI09` 신고 대상 식별 → 이력/영향 조사 → 시험 의뢰 초안 → 제공 결과와 미검사/충돌 확인 → 구성별 대응/재생산 검토 → `UI07` 인계 후보. 신고나 관계만으로 결함과 원인을 확정하지 않는다.
6. **관리자 초안**: `MAP` 클래스·관계·제약 조회 → 격리된 초안 수정 → 좌표 변경과 의미 diff 구분 → 모의 검증 → 저장·검토 요청. 실제 검증 엔진과 운영 배포 계약이 없으므로 운영 적용은 비활성이다.

## 데이터·실행 경계

실제 확보 자료는 `public/evidence`의 ESP32-POE L/L1 WROOM ODS/PDF와 `src/catalog.json`의 고정 출처·해시다. 파일 4개는 모델 4종이 아니다. `src/bom-source.json`은 기존 추출 범위이며 PDF 전체 의미 대조/나머지 모델 전체 검수 완료를 주장하지 않는다. 새 화면용 IO-24·SENSE-4·PWR-12는 독립 합성 보드 3종이며 각 합성 스냅샷의 전체 구성만 제공한다. 이 합성 예시는 원문이 지정한 ESP32-POE-ISO·ESP32-EVB·ESP32-GATEWAY의 실제 전체 BOM 확보를 대신하지 않는다. 따라서 화면에 4모델·5스냅샷을 구성해도 원본 4종·5개 검수 목표 완료로 보고하지 않는다. 그 외 운영 수요·재고·장착·생산·배송·시험은 합성 사례다. 실제 제품 사진은 제공되지 않았다.

조회·Graph·Action·Identity·Agent·Media 포트는 프론트엔드 통합 경계다. 문서의 API 이름은 논리 계약 예시이며 실제 서버 구현을 발견하지 못한 엔드포인트를 확정된 공개 API로 보고하지 않는다. 개발 계정 선택은 UI 권한 시뮬레이션이며 인증 보안 근거가 아니다.

전체 고유 업무 객체/관계 수, 검색 결과 수, 로드 수, 표시 수를 분리한다. 현재 실제 대규모 집계는 미집계이며 10만은 구축 목표다. 기본 상세 300노드/800관계, 누적 1,000노드/2,500관계는 조정 가능한 표시 가드레일이고 전체 영향 조사 범위를 자르는 완료 조건이 아니다.

실제 포함 원본의 행 수·해시 재점검은 [BOM_SOURCE_AUDIT.md](BOM_SOURCE_AUDIT.md)에 기록했다. ODS 74행씩의 비어 있지 않은 데이터 행 범위는 확인했으며, 전체 PDF 의미 대조와 개정/구성 검수는 미완료다.


## 독립 합성 추적 사례

`TRACE-LOT-02 → TRACE-MOUNT-201 → TRACE-U201 → TRACE-SHP-01 → TRACE-ROUND-01`은 `SYN-TRACE-CONFIRMED-01`에 명시된 독립 합성 관계다. 장착 확인 기간과 출하 명세의 직접 보드 ID 참조를 각각 표시한다. 확인 범위 종료는 제거 사건으로 사용하지 않으며 출하 연결은 도착 증거가 아니다.

이 사례는 탐색 상호작용을 확인하기 위한 1대의 독립 시나리오이고 운영 홈의 약속 100대, `s.shipments`, 생산/입고/출하/도착 계산에 포함하지 않는다. 기존 LOT-L07·U104의 출하 연결 미확인은 그대로 유지한다. 합성 관계를 실제 고객/현장 기록으로 보고하지 않는다.
